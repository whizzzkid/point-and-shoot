# Export-format spike (W2.11)

Records first contact between the export bundle format defined by W2.8 (`Session`/`Note`/
`NoteElement`/`RegionCapture`, in [`../../src/shared/schema.ts`](../../src/shared/schema.ts)) and a
real coding agent — before any UI, serializer, or build step exists to produce that format for real.
Per
[the wave 2 plan](../plans/wave-2-core-libraries.md#w211--export-format-spike-feed-a-hand-written-bundle-to-a-real-agent),
this is the cheapest possible moment to find out the format is wrong, and it settles the **default
export size budget** row in
[the plan index's settled-numbers table](../plans/README.md#settled-numbers--the-five-runtime-budgets).

## Method

**The bundle is hand-composed, not generated by product code** — there is no export UI or serializer
to generate it with yet. Its _content_ is grounded in a real page rather than invented, to keep the
test honest:

- The flagged element's selector bundle and style digest were produced by literally calling the
  real, already-shipped `buildSelectorBundle()`
  ([`../../src/shared/selectors.ts`](../../src/shared/selectors.ts)) and `buildStyleDigest()`
  ([`../../src/shared/style-digest.ts`](../../src/shared/style-digest.ts)) against the
  `"Action on light"` button in
  [`../../tests/fixtures/app/light.html`](../../tests/fixtures/app/light.html), via Playwright, so
  the JSON shape and values are exactly what W2.6/W2.7 would emit for this element — not typed-out
  guesses at what those functions return.
- The screenshot is a real capture of that page's `.panel` region, encoded as WebP at quality 0.7
  via `cwebp` (752×189px — under the 1024px longest-edge cap, so `truncated: false`), matching
  {@link RegionCapture.screenshot}'s spec exactly, not a placeholder string.
- The note's free text is hand-written, describing a real, plan-legible bug: `light.html`'s `button`
  rule sets only `font`/`padding`, so the button renders with the browser's bare default chrome and
  doesn't read as clickable — unlike the sibling `dark.html` fixture, whose `button` rule explicitly
  sets `background`/`color`/`border`.

The bundle (`session.json` + `plan.md`, the latter standing in for the markdown projection ADR-0003
says is computed from the JSON at read time, never stored) was handed to a fresh, context-isolated
coding agent (via this session's `Agent` tool) together with a path to an editable copy of
`light.html`, and asked to make the change the note describes — with no hints beyond what the bundle
itself contains. Its output is recorded verbatim below.

To measure the size at which output degrades, the same target note was buried inside a session
containing many additional decoy notes (about the project's other fixture pages, reusing the same
real screenshot bytes to keep per-note size realistic) until the total bundle reached five size
tiers: the single-note baseline, then ~0.43 MB, ~2.13 MB, ~4.26 MB, and ~9.93 MB (60/300/600/1400
notes respectively). Each tier was fed to its own fresh agent with the same instructions.

**Methodology correction, recorded rather than hidden:** the first pass at the three larger tiers
pointed all three agents at the same shared target file (`/tmp/pns-export-spike/target/light.html`),
dispatched concurrently. Only the fastest agent (the smallest, ~0.43 MB bundle) actually applied an
edit; the other two found the file already fixed by the time they got to it and correctly — but
confusingly — reported "no edit was needed," one of them explicitly diagnosing the race. That result
measured dispatch latency, not format degradation, so it was discarded and every tier was rerun
against its own isolated pristine copy of `light.html`. The race-condition transcripts are omitted
below; only the isolated reruns are recorded.

## Transcript: baseline (single note, ~12.6 KB)

Bundle: one note, no decoys. Verbatim agent report:

> Fix applied. Diff:
>
> ```diff
>      button {
>        font: inherit;
>        padding: 6px 12px;
> +      color: #ffffff;
> +      background: #18181b;
> +      border: 1px solid #18181b;
> +      cursor: pointer;
>      }
> ```
>
> **1. What I changed:** The `button` selector in `/tmp/pns-export-spike/target/light.html` had only
> `font` and `padding`, so the "Action on light" button rendered with whatever the browser's default
> UA styling gave it — a background nearly indistinguishable from the `.panel` background (`#efefef`
> vs `#f4f4f5`) and a thin, low-contrast border. I gave it an explicit filled treatment: dark
> background/border (`#18181b`, already the page's body-text color, so it's reusing an existing
> token rather than inventing a new one) with white text and `cursor: pointer`. This makes it pop
> clearly against the light `.panel` background and reads unambiguously as clickable — the
> light-theme analog of what I inferred a dark-theme button with "clear background/border treatment"
> would look like.
>
> **2. What I used from the bundle:**
>
> - `plan.md`'s note text — the core ask ("give this button the same visual affordance... adapted
>   for the light theme") and the specific complaint (no visible bg/border, doesn't read as
>   clickable).
> - The screenshot (`screenshot.webp`, decoded from `session.json`'s embedded base64 — I had to
>   fetch it via the `export-bundle/screenshot.webp` path referenced in `plan.md` since the raw data
>   URI in `session.json` isn't directly viewable) — this was the most useful artifact. It visually
>   confirmed the button blends into the panel with only a faint hairline border, which matched the
>   complaint far better than the computed-style digest did.
> - `session.json`'s `cssPath`/`testIds`/`ariaRoleName` to confirm which element and selector
>   (`button[data-testid="light-action"]`, only one `<button>` on the page) — confirmed via `Read`
>   of `light.html` that there's a single `button` rule, so no selector disambiguation was needed.
>
> **3. What I ignored / didn't need:**
>
> - The `styleDigest.self` computed border (2px, `#000000`) and background (`#efefef`) — these
>   looked like UA-default rendering values from whatever browser captured the report, not authored
>   CSS, and didn't match what I saw in the screenshot (thin gray border, not 2px black). I trusted
>   the screenshot over this digest.
> - Sibling/parent box-metrics (`styleDigest.parent`, `styleDigest.siblings`) — irrelevant to a
>   color/border affordance fix; no layout changes were needed.
> - `pageTitle`, `viewport`, `region.box` coordinates — not needed since I edited the source file
>   directly rather than needing to locate the element on a live page.
>
> **4. Confusion / gaps in the bundle:**
>
> - The report's central comparison — "the same button on the dark page" — points at a page I don't
>   have. No `dark.html` was in the bundle or reachable at the obvious sibling path
>   (`/tmp/pns-export-spike/target/dark.html`), so I couldn't inspect the actual reference treatment
>   I was told to match. I had to guess a plausible "same affordance, adapted for light theme"
>   design (solid dark button, white text) rather than replicate an actual style. If the intent was
>   pixel-parity with a specific dark-theme button (e.g., matching border-radius, specific hover
>   states, or a non-monochrome accent color), the bundle should have included that page's
>   markup/computed styles too, or at least a screenshot of it for comparison.
> - The `styleDigest.self` values (2px black border, `#efefef` background) actively pointed toward a
>   wrong understanding of the _current_ rendered state — they read like UA-default computed style
>   rather than what a human sees, and directly contradicted the screenshot. A bundle that flags
>   "this element looks unstyled" should probably capture the computed style _after_ verifying it's
>   non-default, or at least note when values come from browser defaults vs. authored CSS, since
>   otherwise an agent might "fix" a discrepancy that doesn't exist per the digest and be misled
>   about severity/root cause.
> - No screenshot of the referenced dark page and no indication of what the desired end-state
>   colors/branding should be — I made a judgment call to reuse an existing page color (`#18181b`)
>   rather than pick an arbitrary accent, but a design system reference (or the dark page itself)
>   would have removed the guesswork.

Verified diff (pristine → this run's target file):

```diff
      button {
        font: inherit;
        padding: 6px 12px;
+      color: #ffffff;
+      background: #18181b;
+      border: 1px solid #18181b;
+      cursor: pointer;
      }
+    button:hover {
+      background: #27272a;
+      border-color: #27272a;
+    }
```

## Findings

**The bundle format itself needs no change.** Across all five tiers (12.6 KB → 9.93 MB), a fresh
agent given only the bundle and the target file:

- Correctly identified the flagged element and page every time, including inside a 1,400-note
  haystack of decoys — because `pageUrl` is an exact, greppable key and `Note.text` is a
  self-contained description. No tier produced a wrong-file or wrong-element edit.
- Produced a sound, non-regressive CSS fix every time (verified diffs above), converging on
  essentially the same shape of change (add `background`/`color`/`border`, usually
  `cursor: pointer`) regardless of bundle size.
- Consistently — and correctly — treated `NoteElement.styleDigest`'s computed values as _evidence of
  the current (broken) state_, not as a target to reproduce, once it noticed those values matched
  the browser's UA-default button chrome rather than authored CSS. No agent was misled into "fixing"
  toward the digest's own numbers. This is a robustness property of the format worth keeping, not a
  gap: a digest that only ever reports current computed style, with no separate "intended" field,
  does not tempt an agent to treat it as a target.
- Repeatedly flagged the same real gap: **the note's own text refers to "the dark page" for
  comparison, but nothing in the bundle points at that page** — no note about it, no fixture, no
  screenshot. Every agent handled this by falling back to its own design judgment (reusing the
  page's existing palette) rather than stalling or asking a clarifying question, which is the
  desired degraded-gracefully behavior — but the fixes it produced diverged from each other in exact
  color choice specifically _because_ of that missing reference. This is not a schema gap
  (`Note.text` is already free-form and can name a URL or embed a second screenshot) — it is a
  capture-time UX reminder for W3.6: when a note's text references "the other page/element," the
  capture flow should make it easy to attach that second element's context, not assume prose alone
  carries it. No plan item currently owns this; flagging it here rather than silently dropping it.

**The bundle format's markdown projection (`plan.md`) is not size-invariant, even though the JSON
is.** Starting at the ~4.26 MB tier (600 notes) and reproducing at ~9.93 MB (1,400 notes), the
agent's own tool-output handling silently collapsed a repeated note body in `plan.md` into a
`<<ccr:...>>` placeholder token, because the text recurred verbatim elsewhere in the session. Both
agents caught this only by cross-checking against `session.json` and explicitly flagged that a less
careful pass would have acted on a placeholder instead of the real note text. This did not occur at
300 notes (~2.13 MB) or below. The lesson is not about the JSON schema — `session.json`'s per-note
text was intact and correct at every tier — it is about the design intent already stated in
ADR-0003: **the markdown projection is a convenience view, not a load-bearing artifact.** A future
export UI (W3.6) or plan renderer (W3.7) must not assume an agent that only reads the rendered
markdown got the true note text once a session is large enough for a coding agent's own
context-handling to start summarizing repeated content out from under it. `session.json` remains the
source of truth exactly as already designed; this spike is evidence for keeping that design, not a
reason to change it.

A secondary, milder friction point appeared even earlier: at the ~0.43 MB tier, `session.json`
already exceeded this session's file-reading tool's size threshold, forcing a `grep`/script fallback
instead of a direct read. This did not cause a wrong answer at any tier tested — search-by-exact-key
is a strictly easier task than reading-and-understanding — but it is a second, independent signal
that raw JSON bundles above a few hundred KB stop being something a coding agent (or a human)
casually opens, and should be expected to be searched, not browsed.

## Export size budget

No tier up to and including 300 notes / ~2.13 MB showed any degradation — correct note
identification, correct fix, and no tool-side artifacts. The first concrete degradation signal (the
`plan.md` placeholder-compression bug above) appeared at 600 notes / ~4.26 MB and recurred at 1,400
notes / ~9.93 MB. Even at those sizes the agent still produced a correct fix by falling back to the
JSON, but that fallback is exactly the kind of thing a warning threshold should keep users from
routinely needing.

**Measured default export size budget: `2 MB`.** This confirms rather than revises the previous
provisional guess — the largest tier with zero degradation signal (~2.13 MB) sits right at that
value, and the first observed failure mode begins roughly a further 2 MB beyond it, leaving the
warning threshold real margin before a session actually needs to hit the failure mode W3.6 warns
about.

| Budget                     | Value  | Basis                                                                                                                                                                    |
| -------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Default export size budget | `2 MB` | Measured here: no degradation through ~2.13 MB (300 notes); first degradation (`plan.md` placeholder-compression of repeated note text) observed at ~4.26 MB (600 notes) |

No amendment to W3.7 is needed — the record shape and the markdown-is-a-projection design in
ADR-0003 already anticipate exactly the failure mode this spike found.
